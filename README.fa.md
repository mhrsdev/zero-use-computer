# computer-use

یک قابلیت **استفاده از کامپیوتر (computer use)** به سبک Codex برای ایجنت‌ها، نوشته‌شده با Rust. این پروژه همان کاری را برای ایجنت شما می‌کند که قابلیت computer use اپ Codex انجام می‌دهد: دیدن و کار کردن با اپ‌های گرافیکی واقعی — کلیک، تایپ، خواندن وضعیت روی صفحه و انجام کارهای چنداپلیکیشنی — ساخته‌شده روی **API دسترس‌پذیری (accessibility)** بومی هر سیستم‌عامل به‌همراه **اسکرین‌شات**، و با **تأیید جداگانه برای هر اپ**.

این یک ماژول مستقل است: می‌توانید آن را به‌صورت یک **سرور MCP** اجرا کنید (با Codex، Claude Code یا هر ایجنت سازگار با MCP کار می‌کند)، یا **کتابخانه** آن را داخل ایجنت خودتان استفاده کنید.

> English guide: [README.md](README.md).

## چرا معماری‌اش مثل Codex است؟

computer use در Codex «اول دسترس‌پذیری» است: درخت accessibility اپ را می‌خواند، روی عناصر به‌صورت معنایی عمل می‌کند و فقط وقتی مجبور شود سراغ پیکسل می‌رود. این پروژه دقیقاً همین معماری و رفتار را دارد:

- **درخت accessibility + اسکرین‌شات.** ابزار `get_app_state` یک درخت accessibility هرس‌شده و **شماره‌دار** به‌همراه یک اسکرین‌شات از پنجره برمی‌گرداند. هر اکشن روی یک `element_index` انجام می‌شود و از اکشن بومی سیستم (فشردن، تنظیم مقدار، تغییر وضعیت و…) استفاده می‌کند؛ برای همین حتی روی پنجره‌های پس‌زمینه هم کار می‌کند.
- **شماره‌ها فقط تا نوبت بعد معتبرند.** ایندکس عناصر فقط تا فراخوانی بعدیِ `get_app_state` معتبر است؛ فراخوانی‌های بعدی یک **diff** برمی‌گردانند (مگر اینکه `disable_diff` بدهید) تا مصرف توکن پایین بماند.
- **حافظهٔ صفحه (فراتر از Codex).** وقتی اپ به صفحه‌ای برمی‌گردد که مدل قبلاً دیده و تحلیل کرده — یک صفحه برگشته، دیالوگی بسته شده، پنلی دوباره باز شده — موتور آن را می‌شناسد، همان شماره‌های قبلی عناصر را برمی‌گرداند و فقط تفاوت‌ها را می‌فرستد: نه درخت جدید، نه اسکرین‌شات جدید برای تحلیل دوباره. بخش «حافظهٔ صفحه و کش» را ببینید.
- **همان ده ابزاری** که پلاگین Computer Use در Codex دارد — `list_apps`، `get_app_state`، `click`، `perform_secondary_action`، `set_value`، `select_text`، `scroll`، `drag`، `press_key`، `type_text` — به‌علاوهٔ `launch_app`.
- **تأیید و ایمنی.** هر اپ قبل از کنترل‌شدن باید تأیید شود (یک‌بار / برای این نشست / همیشه)، و ترمینال‌ها، پرامپت‌های رمز و امنیت سیستم‌عامل، و خودِ اپ میزبانِ ایجنت هرگز قابل کنترل نیستند.

## ابزارها

| ابزار | کارش چیست |
|------|-----------|
| `list_apps` | فهرست اپ‌های در حال اجرا (شناسه، pid، وضعیت پنجره). |
| `launch_app` | اجرای یک اپ با نام/شناسهٔ بسته/فایل اجرایی و انتظار تا باز شدن پنجره. |
| `get_app_state` | درخت accessibility شماره‌دارِ پنجره **+ یک اسکرین‌شات**. اول هر نوبت صدا بزنید. |
| `click` | کلیک روی یک عنصر با `element_index` (از اکشن بومی‌اش استفاده می‌کند) یا روی مختصات `x`/`y` بر حسب پیکسلِ اسکرین‌شات. |
| `perform_secondary_action` | اکشن غیرکلیکیِ فهرست‌شده برای عنصر (`show_menu`, `increment`, `expand`, `toggle`…). |
| `set_value` | تنظیم مستقیم متن یک فیلد، اسلایدر، یا چک‌باکس/سوییچ. |
| `select_text` | انتخاب یک زیررشته (یا کل متن) در یک عنصر متنی. |
| `scroll` | اسکرول یک عنصر یا ناحیهٔ زیر یک نقطه. |
| `drag` | کشیدن بین عناصر یا نقاط. |
| `press_key` | یک کلید یا میان‌بر، مثل `cmd+s`، `ctrl+shift+t`، `Down Down Return`. |
| `type_text` | تایپ در عنصری که فوکوس دارد. |
| `find_element` | جست‌وجوی درخت بر اساس نقش/نام/متن؛ فقط عناصر مطابق را با ایندکس برمی‌گرداند. |
| `wait_for` | صبر تا ظاهر شدن یک عنصر (نقش/نام/متن + وضعیت)، با مهلت زمانی. |
| `screenshot` | عکس از **کل صفحه**، یک **ناحیهٔ مشخص از صفحه**، یا یک پنجره؛ با شماره‌گذاری اختیاری عناصر روی تصویر. |
| `batch` | اجرای چند ابزار در یک فراخوانی (پر کردن فرم و بعد Submit). |
| `get_clipboard` / `set_clipboard` | خواندن/نوشتن کلیپ‌بورد سیستم. |

علاوه بر ده ابزار Codex، این ابزارهای اضافه (`find_element`، `wait_for`، `batch`، اسکرین‌شاتِ ناحیه/کل‌صفحه، کلیپ‌بورد) رفت‌وبرگشت و مصرف توکن را کم می‌کنند، و موتور دو لایهٔ ایمنی دارد که Codex به عهدهٔ مدل می‌گذارد: **محافظ اکشن** (تأیید کارهای حساس مثل Send/Delete/Pay) و **لاگ حسابرسی** اختیاری.

قرارداد کامل کاری که مدل باید دنبال کند در [`skill/SKILL.md`](skill/SKILL.md) است.

## حافظهٔ صفحه و کش

بیشترِ توکن و زمان یک ایجنت صرف دوباره‌خواندن صفحه‌ها می‌شود. موتور چند لایه کش دارد تا مدل هیچ‌وقت یک چیز را دو بار نگاه نکند:

| لایه | چه چیزی را صرفه‌جویی می‌کند | تنظیم |
|---|---|---|
| **حافظهٔ صفحه** | هر صفحه‌ای که به مدل نشان داده شده به‌صورت فشرده به خاطر سپرده می‌شود (برای هر عنصر: هش‌ها، شماره و خط نمایشی‌اش). اگر نمای فعلی با یک صفحهٔ قبلی جور باشد، شماره‌های قبلی برمی‌گردند و فقط تفاوت با **چیزی که مدل آن موقع دیده** فرستاده می‌شود. | `[cache] enabled`، `max_screens`، `max_memory_kb`، `match_threshold` |
| **حذف اسکرین‌شات تکراری** | از هر اسکرین‌شاتِ ارسالی یک اثرانگشت روشنایی (شبکهٔ ۶۴ خانه‌ای) نگه داشته می‌شود؛ تصویرِ یکسان از همان صفحه دوباره کدگذاری و ارسال نمی‌شود (`screenshot=true` همیشه تصویر می‌فرستد). | `dedupe_screenshots`، `pixel_grid`، `pixel_tolerance` |
| **استفادهٔ دوباره از خواندن اخیر** | اگر از آخرین خواندن درخت/فهرست پنجره‌ها لحظه‌ای گذشته و بینشان اکشنی انجام نشده، همان استفاده می‌شود (مثلاً `find_element` و بلافاصله `get_app_state`، یا `get_app_state` درست بعد از گزارش تغییرات یک اکشن). هر اکشن آن را باطل می‌کند. | `snapshot_ttl_ms` |
| **فهرست اپ‌ها** | فهرست اپ‌های در حال اجرا کوتاه‌مدت بین فراخوانی‌ها نگه داشته می‌شود. | `timing.app_cache_ms` |

یک رفت‌وبرگشت کامل — دیدن صفحه، زدن دکمه، تأیید، برگشتن — این شکلی است:

</div>

```text
get_app_state  → App: Mail … · screen #1 (new)        درخت کامل + اسکرین‌شات
click "Delete" → State after the action: now on screen #2 (new), window "Confirm":
                 6 dialog "Confirm" / 7 text "Delete 3 messages?" / 8 button "OK"
click 8        → State after the action: back on screen #1 (seen before), window "Inbox":
                 Changes since you last saw screen #1 (+ added, ~ changed, - removed) …
                 - 14 list item "Meeting notes"
get_app_state  → … · screen #1
                 Screenshot: not attached …  Tree: No changes …
```

<div dir="rtl">

چطور کار می‌کند:

- **شناسایی صفحه.** هر عنصر یک کلید هویت دارد (شناسهٔ خودِ سیستم، یا زنجیرهٔ هشِ نقش + برچسب + جایگاه بین هم‌سطح‌ها) و یک «شکل» (همان هش ساختاری). تطبیق با صفحه‌های قبلی با شباهت Jaccardِ شکل‌ها انجام می‌شود (`match_threshold`، پیش‌فرض ۰٫۸)؛ برای همین دیالوگی که بسته و دوباره باز شده هم شناخته می‌شود، با اینکه اشیای accessibility‌اش جدیدند.
- **معنای شماره‌ها عوض نمی‌شود.** هر شماره برای هر اپ فقط یک بار داده می‌شود و دوباره مصرف نمی‌شود. عناصر صفحهٔ برگشتی همان شماره‌هایی را می‌گیرند که مدل آن موقع دیده؛ شماره‌ای از صفحه‌ای که دیگر نیست به‌جای کلیک روی چیز دیگر، با خطای «unknown element_index» رد می‌شود.
- **مبنا همان چیزی است که مدل دیده.** diffها نسبت به چیزی حساب می‌شوند که واقعاً به مدل نشان داده شده، نه آخرین خواندن داخلی. پس `find_element`، `wait_for` و گزارشِ تغییراتِ بریده‌شده هیچ تغییری را از `get_app_state` بعدی پنهان نمی‌کنند، و در `batch` فقط تصویری «دیده‌شده» حساب می‌شود که واقعاً برگشته.
- **دنبال کردن دیالوگ‌ها.** وقتی اکشنی پنجرهٔ جدیدی باز می‌کند (دیالوگ، منو)، گزارش تغییرات و `get_app_state` بعدی به آن می‌روند (`follow_new_windows`)؛ وقتی بسته شد، پنجرهٔ زیرش شناخته می‌شود.
- **اسکرین‌شات قبلی معتبر می‌ماند.** اسکرین‌شاتِ قبلیِ صفحهٔ برگشتی برای کلیک با `x`/`y` همچنان کار می‌کند (اگر پنجره جابه‌جا شده باشد جابه‌جا می‌شود؛ اگر اندازهٔ پنجره عوض شده باشد کنار گذاشته و تصویر تازه فرستاده می‌شود).

اندازه‌گیری روی `gtk3-widget-factory` با رفت‌وبرگشت بین دو صفحه: برگشتن به یک صفحه **حدود ۷۹ توکن** هزینه دارد به‌جای **حدود ۲۵۰۰** (۱۲۵۰ متن + ۱۲۶۵ تصویر) و حدود ۱۵٪ سریع‌تر است چون چیزی کدگذاری نمی‌شود. حافظه برای هر صفحه حدود ۷٫۵ KiB است و حداکثر مصرف رم پروسه تغییری نکرده.

## معماری

- **موتور (engine)** مستقل از سکو است و همهٔ رفتاری را دارد که باید همه‌جا یکسان باشد: هرس‌کردن درخت خام accessibility به یک نمای شماره‌دارِ کم‌حجم، تخصیص ایندکس پایدار برای هر نوبت، گرفتن diff بین اسنپ‌شات‌ها، نگاشت پیکسل اسکرین‌شات به مختصات صفحه، و اعمال سیاست تأیید.
- هر **backend** یک آداپتور نازک روی یک سیستم‌عامل است:

| | macOS | Windows | Linux |
|---|---|---|---|
| درخت و اکشن‌ها | Accessibility (AX) API | UI Automation | AT-SPI2 روی D-Bus |
| ورودی | `CGEvent` که به pid مقصد فرستاده می‌شود (پس‌زمینه، نشانگر تکان نمی‌خورد) | `SendInput` | XTest |
| تصویربرداری | `CGWindowListCreateImage` | `PrintWindow` | X11 `GetImage` |

## آماده‌سازی هر سکو

- **macOS** — به اپ میزبان مجوز **Accessibility** و **Screen Recording** بدهید. ورودی به فرایند مقصد فرستاده می‌شود، پس نشانگر کاربر تکان نمی‌خورد.
- **Windows** — برای UI Automation مجوز خاصی لازم نیست؛ ورودی مختصاتی با `SendInput` روی دسکتاپ فعال انجام می‌شود.
- **Linux** — به یک باس accessibility از نوع AT-SPI2 و یک نمایشگر X11 نیاز دارد. برای ابزارک‌تان accessibility را روشن کنید (مثلاً GTK وقتی باس a11y موجود باشد پل at-spi را بار می‌کند). Wayland برای ورودی/تصویربرداریِ مصنوعی پشتیبانی نمی‌شود؛ از نشست X11 (یا XWayland) استفاده کنید.

## تنظیمات (همه‌چیز قابل‌تنظیم است)

تمام رفتارها یک تنظیم در فایل `~/.computer-use/config.toml` هستند (مسیر با `$COMPUTER_USE_HOME` یا `--config` قابل تغییر است). از قالب مستند شروع کنید؛ **همهٔ گزینه‌ها با مقدار پیش‌فرض و توضیح** در آن هست:

</div>

```bash
computer-use-mcp config init                 # ساخت فایل تنظیمات مستند
computer-use-mcp config show                 # تنظیمات مؤثر فعلی
computer-use-mcp config keys                 # فهرست همهٔ کلیدها
computer-use-mcp config set screenshot.attach always
computer-use-mcp config set sensitive.terminals ask
computer-use-mcp config add approvals.always_allow com.googlecode.iterm2
computer-use-mcp config add tools.disabled drag
computer-use-mcp config unset tree.max_nodes   # برگشت به پیش‌فرض
computer-use-mcp config check                # اعتبارسنجی + پیدا کردن کلید غلط‌املایی
```

<div dir="rtl">

- هر تغییر **قبل از ذخیره اعتبارسنجی می‌شود** (مقدار نامعتبر یا کلید ناشناخته با پیام واضح رد می‌شود) و کامنت‌های فایل حفظ می‌شوند.
- سرورِ در حال اجرا **فایل را خودکار دوباره می‌خواند** (`hot_reload`) و اگر فهرست ابزارها عوض شد به کلاینت MCP خبر می‌دهد — نیازی به ری‌استارت نیست.
- پرچم‌های خط فرمان (`--approval`، `--text-only`، `--log`، `--http`…) بر فایل مقدم‌اند و بعد از reload هم اعمال می‌مانند.
- ایجنت هیچ ابزاری برای تغییر تنظیمات ندارد.

| بخش | چه چیزی را کنترل می‌کند |
|---|---|
| `[approvals]` | حالت تأیید (`prompt`/`allowlist`/`allow_all`)، مجاز/ممنوع کردن تک‌تک اپ‌ها |
| `[sensitive]` | ترمینال، مدیر رمز، پرامپت امنیتی، اپ ایجنت، پروسهٔ خودی: هر کدام `block`/`ask`/`allow` + الگوهای دلخواه |
| `[guard]` | تأیید/اجازه/منع کارهای حساس (Send/Delete/Pay…) و فهرست کلیدواژه‌ها |
| `[tools]` | مخفی کردن ابزارها، فهرست مجاز، توضیحات `compact` یا `full` |
| `[screenshot]` | روشن/خاموش، `attach` = `auto`/`always`/`never`، اندازه، PNG/JPEG، کیفیت، فشرده‌سازی، فیلتر تغییر اندازه |
| `[tree]` | محدودیت‌ها، طول متن، تورفتگی، نمایش اکشن‌ها/وضعیت‌ها، diff، گزارش تغییرات |
| `[timing]` | مکث بعد از اکشن، فاصلهٔ کلیدها، کش فهرست اپ‌ها، پیش‌فرض‌های `wait_for` |
| `[cache]` | روشن/خاموش کردن حافظهٔ صفحه، تعداد صفحه‌ها و سقف حافظه، آستانهٔ تطبیق، حذف اسکرین‌شات تکراری و حساسیتش، بازهٔ استفادهٔ دوباره از خواندن اخیر |
| `[audit]` | لاگ حسابرسی و مسیرش |
| `[server]` | سیاست تأیید بدون کلاینت، سطح لاگ، آدرس و توکن HTTP |
| `[linux]` / `[macos]` / `[windows]` | تنظیمات مخصوص هر سیستم‌عامل |
| سطح بالا | `clipboard`، `text_only`، `follow_new_windows`، `hot_reload`، `launch_timeout_secs` |

اپ‌های حساس به‌طور پیش‌فرض مسدودند؛ آن‌ها را **یک دسته یا یک اپ در هر بار** باز کنید. سیاست مدیریتی (`managed.toml`) همیشه بر تنظیمات کاربر مقدم است.

### تنظیمات کاهش مصرف توکن

- `tools.descriptions = "compact"` (پیش‌فرض): فهرست ابزارها با **هر** درخواست به مدل فرستاده می‌شود؛ حالت فشرده آن را از حدود ۳۳۰۰ به حدود ۱۳۶۰ توکن می‌رساند. مخفی کردن ابزارهای غیرلازم (`tools.disabled`) باز هم کمترش می‌کند.
- `screenshot.attach = "auto"` (پیش‌فرض): تصویر فقط برای اولین نمای پنجره، تغییر بزرگ، یا درختی که تقریباً عنصر تعاملی ندارد. diffِ یک پنجرهٔ بدون تغییر حدود ۶۰ توکن می‌شود به‌جای حدود ۱۳۰۰.
- `cache.enabled` و `cache.dedupe_screenshots` (پیش‌فرض روشن): صفحه‌ای که مدل قبلاً دیده حدود ۸۰ توکن هزینه دارد به‌جای درخت کامل و تصویر؛ اسکرین‌شاتِ بدون تغییر هرگز دو بار فرستاده نمی‌شود.
- `screenshot.max_dimension`: توکن تصویر با عرض×ارتفاع رشد می‌کند (۱۰۲۴ پیکسل حدود ۳۶٪ کمتر از ۱۲۸۰). `text_only = true` تصویر را کاملاً حذف می‌کند.

### ترنسپورت راه‌دور (اختیاری)

با فیچر `http` می‌توانید MCP را روی HTTP برای یک ایجنت راه‌دور اجرا کنید:

</div>

```bash
cargo build --release -p computer-use-mcp --features http
computer-use-mcp serve --http 127.0.0.1:8787 --http-token "$TOKEN" --approval allow-all
# یا در تنظیمات: server.http_addr و server.http_token
```

<div dir="rtl">

روی HTTP کانال تأیید تعاملی وجود ندارد، پس با سیاست تأیید مشخص اجرا کنید، توکن bearer بگذارید و فقط روی localhost یا شبکهٔ مورد اعتماد bind کنید.

## کارایی

اندازه‌گیری با `examples/bench.rs` روی لینوکس (Xvfb و AT-SPI) با یک دیالوگ کوچک GTK و `gtk3-widget-factory` (حدود ۵۰۰ عنصر). تعداد توکن تخمینی است.

| | قبل | بعد |
|---|---|---|
| `get_app_state` اپ بزرگ | ۵۳۳ میلی‌ثانیه | **۸۷ میلی‌ثانیه** |
| `get_app_state` تکراری (diff) اپ بزرگ | ۵۰۷ ms، حدود ۱۳۴۶ توکن | **۶۷ ms، حدود ۶۶ توکن** |
| `find_element` اپ بزرگ | ۴۷۳ ms | **۷۲ ms** |
| `get_app_state` تکراری، دیالوگ کوچک | ۱۹ ms، حدود ۲۱۹ توکن | **۲٫۴ ms، حدود ۵۸ توکن** |
| تعریف ابزارها در هر درخواست به مدل | حدود ۳۳۰۰ توکن | **حدود ۱۳۶۰ توکن** |
| حداکثر مصرف رم | ۱۹٫۷ MiB | **۱۶٫۴ MiB** |
| برگشت به صفحه‌ای که قبلاً دیده شده، اپ بزرگ | حدود ۲۵۱۶ توکن (درخت + تصویر) | **حدود ۷۹ توکن، بدون تصویر** |
| `get_app_state` درست بعد از یک اکشن یا `find_element` | ۷۱ ms | **کمتر از ۱ ms** (خواندن قبلی استفاده می‌شود) |

منشأ بهبودها: در لینوکس پرس‌وجوهای AT-SPI به‌صورت هم‌زمان (pipelined) ارسال می‌شوند؛ در مک همهٔ ویژگی‌های هر عنصر با یک فراخوانی AX خوانده می‌شود؛ در ویندوز کل پنجره با یک CacheRequest گرفته می‌شود؛ تصویرها با فیلتر سریع کوچک و بدون کپی بافر پیکسل کدگذاری می‌شوند (کانال آلفا در همان بافر حذف می‌شود)؛ و موتور فهرست اپ‌ها، خواندن‌های اخیر و صفحه‌های دیده‌شده را کش می‌کند و درخت قبلی را جابه‌جا (نه کپی) می‌کند. مسیرهای مک و ویندوز کامپایل و بررسی شده‌اند ولی هنوز روی سخت‌افزار واقعی اندازه‌گیری نشده‌اند.

## ایمنی

اپ‌های حساس به‌طور پیش‌فرض مسدودند ولی قابل‌تنظیم‌اند (بالا را ببینید)؛ اولین استفاده از هر اپ دیگر با تأیید کنترل می‌شود. علاوه بر آن، **محافظ اکشن** کارهای حساس (Send/Delete/Pay) را در سطح موتور تأیید می‌گیرد — نه صرفاً با اعتماد به مدل — و یک **لاگ حسابرسی** اختیاری هر فراخوانی را ثبت می‌کند. به مدل هم گفته شده (در فایل skill) که پیش از این کارها مکث کند.
